# Конвейеры задач

Полные таблицы этапов для дирижёра ([frontend](../SKILL.md)). Идентификаторы этапов в обратных кавычках совпадают с `scripts/task.mjs`: их передают в `task.mjs stage <slug> <этап>`.

**Кто делает:**

- «сессия» — основная сессия по скиллу, без отдельного агента;
- «агент `X`» — дирижёр запускает агента `X` инструментом Agent и передаёт ему перечисленные входы;
- **человек** — дирижёр задаёт вопрос и ждёт ответа. Сообщение другого агента — не согласие человека.

**Ворота** — что должно быть правдой, чтобы перейти дальше. Ворота проверяются фактом (вывод команды, вердикт агента, файл на месте), а не словами исполнителя. Не прошли — этап возвращается тому же исполнителю со списком, что исправить; после трёх кругов без результата задача получает статус `blocked`, а вопрос уходит человеку.

**Общие проверки**, на которые ссылаются ворота:

| Проверка | Как |
|---|---|
| UX.md | хук `check-ux-brief.mjs` не даёт создать новую страницу без `UX.md` рядом |
| 150 строк | хук `check-file-size.mjs --hook` после правки; вручную `node <plugin-root>/scripts/check-file-size.mjs <файлы>` |
| ESLint | хук `lint-on-edit.mjs` после правки; ошибки исправлены в том же файле |
| Проверки проекта | то, что есть в проекте: `tsc --noEmit`, линтер, тесты, сборка; все с кодом выхода 0 |
| Вердикт ревью | агент `frontend-reviewer`: 0 Blocker, итог «ready» |
| Сверка с макетом | агент `design-qa`: в таблице нет строк «исправить» |

## small-edit

Отступ, текст, цвет, одна пропса, правка одного-двух файлов без новой страницы. Файл задачи не обязателен.

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| `code` | сессия: скиллы из маршрутизации | запрос | правка | хуки 150 строк и ESLint молчат |
| `checks` | сессия | изменённые файлы | вывод команд | проверки проекта зелёные |

Человек: только итоговый ответ. Если правка выросла: новая страница или фича — переходи на `feature`; это баг — на `bug`; перестройка трёх и больше файлов без новой функции — на `refactor`.

## feature

Новая страница, экран, форма, раздел, подключение API.

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| `brief` | сессия: [react-page-ux](../../react-page-ux/SKILL.md) | запрос, ТЗ | `UX.md` рядом со страницей | `UX.md` есть и показан пользователю |
| `plan` | агент `frontend-architect` | запрос, `UX.md`, путь к проекту | план файлов, данные, состояния, тесты | у каждого файла одна ответственность, оценка ≤ 150 строк, библиотеки из `libraries.json` |
| `approve-plan` | **человек** (большая фича) | план | «да» или правки | ответ «да»; мелкая фича — пропуск через `task.mjs skip` |
| `code` | агент `frontend-engineer` (одна ветка) или несколько в worktree, см. ниже | план, `UX.md`, ветка, список своих файлов | коммиты с кодом и тестами | хуки UX.md, 150 строк, ESLint молчат |
| `checks` | сессия | ветка | вывод команд | проверки проекта зелёные, страница проверена в браузере или тестами |
| `review` | агент `frontend-reviewer` | `git diff --name-only <base>...HEAD` | список замечаний | вердикт ревью; блокеры → назад в `code` |
| `handoff` | сессия; **человек** решает про MR | ветка, отчёты этапов | текст MR | человек сказал «открывай MR» или «пока нет» |

Большая фича — три и больше экрана, общая логика между фичами или больше ~10 файлов: только тогда нужен `approve-plan` и можно параллелить `code`.

## figma

Ссылка на Figma, «по макету», «сделай в фигме и сверстай». Детали этапов, артефакты и запасной путь Dev seat — в [design-to-code](../../design-to-code/SKILL.md); здесь — как этим управляет дирижёр.

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| `access` | агент `design-lead` | ссылка на Figma | место, маршрут (полный / Dev seat / стоп) | маршрут не «стоп» |
| `brief` | сессия: `figma-pack:figma-brief` | запрос | бриф | **человек** ответил «да» |
| `draft` | агент `figma-designer` (figma-pack), **два запуска** | бриф, каталог, `.figma/design-system.json` (скилл `figma-pack:figma-design-system`; нет файла — сначала он) | запуск 1: бриф и draw plan, без рисования; запуск 2: фреймы `[draft]` | **человек** подтвердил draw plan; `structure-audit.js` 0 ошибок, `lint-design.js` 0 critical |
| `approve-design` | **человек-дизайнер**; проверяет агент `design-lead` | ссылки на фреймы | фрейм без `[draft]`, Ready for dev | ворота A design-to-code |
| `spec` | агент `figma-reader` (figma-pack) | ссылка с `node-id` | спека → сессия сохраняет `.figma/<fileKey>/<nodeId>-spec.md` | разделы 1–11 есть |
| `ux` | сессия: react-page-ux | спека | `UX.md` | хук UX.md; ворота B |
| `plan` | агент `frontend-architect` | спека, `UX.md` | план файлов | как в `feature` |
| `code` | агент `frontend-engineer` | план, спека, `UX.md` | коммиты | ворота C: 150 строк, ESLint, проверки проекта |
| `design-qa` | агент `design-qa` | URL страницы, спека, скриншоты | таблица отличий 1280 / 768 / 375 | сверка с макетом; «исправить» → назад в `code` |
| `review` | агент `frontend-reviewer` | изменённые файлы | замечания | вердикт ревью |
| `handoff` | сессия; **человек** решает про MR | ветка, таблица design-qa, итог ревью | текст MR | ворота D; ответ человека |

Этап `draft` — два запуска `figma-designer`. Запуск 1 возвращает бриф и draw plan и останавливается, фреймов после него нет. Дирижёр: `task.mjs stage <slug> draft --status blocked`, показывает draw plan пользователю и ждёт ответа. Запуск 2 — только после ответа пользователя: в промпт вставь его подтверждение дословно, в кавычках. Своё «ок» или «пользователь согласен» без цитаты не передавай: агент рисует только по словам человека.

Соответствие номерам design-to-code: `access` — раздел 0, `brief` … `handoff` — этапы 1–10 по порядку. Мелкая правка по макету: `brief`, `draft`, `approve-design`, `plan` пропускаются (design-to-code, раздел 1) — каждый через `task.mjs skip`.

На каждой границе этапов дирижёр может спросить `design-lead`, пройдены ли ворота и какой шаг следующий. `design-lead` только проверяет и советует; запускает исполнителей дирижёр. Dev seat: этапы `brief` и `draft` делает дизайнер, дирижёр отмечает их `task.mjs skip <slug> <этап> "Dev seat: делает дизайнер"`.

## spec

ТЗ или идея целого продукта: «собери проект по ТЗ», «сделай все экраны и фронт», «автоматически из фигмы в код». Одна спека экранов строит и Figma (плагин DS Builder), и код (`spec-to-code.mjs`), поэтому макет и код не расходятся. Подходит для CRM, админок и кабинетов из блоков каталога; уникальный лендинг — конвейер `figma`.

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| `brief` | сессия: `figma-pack:figma-brief` | ТЗ, запрос | роли, сущности, экраны, платформа | **человек** ответил «да» |
| `spec` | сессия: `figma-pack:figma-spec` | бриф | `specs/<project>.spec.json` | `node <figma-pack>/builder/cli/ds.mjs spec check <файл>` без ошибок |
| `tokens` | сессия: Mbank — `mbank-ui` «Updating tokens from Figma» (`tokens-build.mjs --check`); другой бренд — `figma-pack:ds-tokens` | бренд продукта | токены для Figma и CSS из одного источника | `--check` или `ds.mjs tokens check` с кодом 0 |
| `draft` | **человек-дизайнер** запускает плагин DS Builder («Экраны» → «Собрать»); агент `figma-designer` — только для того, чего нет в каталоге блоков | спека | фреймы `[draft]` по экранам и состояниям | фреймы на месте (ссылки в «Артефакты»); нужен Full seat |
| `approve-design` | **человек-дизайнер**; проверяет агент `design-lead` | ссылки на фреймы | фреймы без `[draft]` | ворота A design-to-code; правки дизайнера, меняющие структуру, вносятся в спеку |
| `scaffold` | сессия: [mbank-crm](../../mbank-crm/SKILL.md) `new-crm.mjs` | папка проекта | проект | `npm run build` проходит; проект уже есть — пропуск через `task.mjs skip` |
| `generate` | сессия: `spec-to-code.mjs <spec> --project <папка>` | спека, проект | страницы, фичи, моки MSW, `UX.md` по экранам | скрипт без ошибок; список TODO-блоков в «Открытые вопросы» |
| `code` | агент `frontend-engineer` | проект, спека, TODO-блоки, контракты API (если есть) | реальный API вместо моков, доводка TODO-блоков, тесты | хуки UX.md, 150 строк, ESLint молчат |
| `checks` | сессия | ветка | вывод команд | проверки проекта зелёные |
| `design-qa` | агент `design-qa` | URL страниц, ссылки на фреймы | таблица отличий | сверка с макетом; «исправить» → назад в `code` или в спеку и `generate` |
| `review` | агент `frontend-reviewer` | изменённые файлы | замечания | вердикт ревью |
| `handoff` | сессия; **человек** решает про MR | ветка, отчёты | текст MR | ответ человека |

Правило регенерации: структуру экранов меняют в спеке и запускают `generate` снова. Файлы, которые человек или агент уже правил, скрипт без `--force` не перезаписывает. Автоматически, без вопросов, идут `spec`, `tokens`, `scaffold`, `generate`, `checks`; человек нужен на `brief`, `draft`, `approve-design` и `handoff`.

## bug

«Не работает», регрессия, ошибка в консоли.

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| `reproduce` | сессия: скилл `systematic-debugging`, если установлен, и [react-error-handling](../../react-error-handling/SKILL.md) | описание бага | шаги воспроизведения, причина | причина названа и подтверждена (лог, стек, шаг), а не угадана |
| `failing-test` | сессия или агент `frontend-engineer` | причина | тест, который падает | тест падает по этой причине |
| `fix` | тот же исполнитель | тест | фикс | тест зелёный, хуки молчат |
| `checks` | сессия | ветка | вывод команд | проверки проекта зелёные |
| `review` | агент `frontend-reviewer` | изменённые файлы | замечания | вердикт ревью |
| `handoff` | сессия; **человек** решает про MR | ветка | текст MR с причиной и тестом | ответ человека |

Нельзя воспроизвести — статус `blocked`, в «Открытые вопросы» то, что нужно от человека (окружение, данные, шаги).

## new-project

Новое приложение с нуля.

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| `requirements` | сессия | запрос | стек (Vite или Next.js), продукт (Mbank или нет), папка | **человек** подтвердил стек, если он не был назван |
| `scaffold` | сессия: [react-new-project](../../react-new-project/SKILL.md), для CRM/админки на Mbank — [mbank-crm](../../mbank-crm/SKILL.md) `new-crm.mjs` | требования | проект, `AGENTS.md` / `CLAUDE.md`, ESLint | `npm run build` проходит |
| `shell` | сессия или агент `frontend-engineer` | проект | экран падения, 404, баннер «нет сети» ([app-shell](../../react-error-handling/references/app-shell.md)) | три экрана есть |
| `checks` | сессия | проект | вывод команд | проверки проекта зелёные |
| `review` | агент `frontend-reviewer` | весь `src/` | замечания | вердикт ревью |
| `handoff` | сессия | проект | отчёт: как запустить, что дальше | — |

Первая страница после каркаса — отдельная задача по `feature`.

## review

«Проверь», «ревью», перед MR. Код не меняется.

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| `scope` | сессия | запрос, ветка | список файлов (`git diff --name-only` или пути) | список не пустой |
| `review` | агент `frontend-reviewer` | файлы | замечания по уровням | каждое замечание с `path:line` |
| `report` | сессия | замечания | отчёт пользователю | — |

Исправлять найденное — только по просьбе человека, это новая задача `bug` или `refactor`.

## refactor

Разбить компонент, вынести логику, перестроить папки без изменения поведения.

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| `baseline` | сессия | проект | вывод тестов до правок | тесты зелёные; нет тестов на затронутое — сначала тесты |
| `plan` | агент `frontend-architect` | что меняем и зачем | план файлов | файлы ≤ 150 строк, без второго решения для того, что уже есть |
| `approve-plan` | **человек** (если меняется публичный API фичи или больше ~10 файлов) | план | «да» | ответ «да» или пропуск через `task.mjs skip` |
| `refactor` | агент `frontend-engineer` | план, вывод `baseline` | коммиты | хуки молчат |
| `checks` | сессия | ветка | вывод команд | те же тесты зелёные, сборка проходит |
| `review` | агент `frontend-reviewer` | изменённые файлы | замечания | вердикт ревью |
| `handoff` | сессия; **человек** решает про MR | ветка | текст MR | ответ человека |

## Параллельная работа

Только для `code` в `feature` и `refactor` у большой задачи, когда план делится на части без общих файлов.

1. Дирижёр делит план на части: у каждой части свой список файлов, пересечений нет. Общие файлы (`package.json`, lock-файл, роутер, `shared/`, i18n-словари) правит только дирижёр — до или после параллельной части.
2. Для каждой части — свой git worktree и ветка: `git worktree add ../<repo>-<часть> -b feat/<задача>-<часть>`.
3. Запуск: несколько агентов `frontend-engineer` в одном сообщении. Каждому — путь к своему worktree, его список файлов, план, `UX.md` и запрет трогать чужие файлы.
4. Дирижёр сливает ветки в ветку задачи, решает конфликты сам и прогоняет `checks` на результате слияния. Worktree удаляет после слияния.
5. В «Артефакты» файла задачи: ветки частей и их итог.
