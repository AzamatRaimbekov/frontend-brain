## Контекст

`get_design_context` возвращает референс в виде React + Tailwind. Агент вставляет его как есть — и в
проект попадают hex-цвета, пиксели, placeholder-картинки и ещё одна копия кнопки рядом с `shared/ui`.

## Решение

Порядок вызовов (так рекомендует Figma в своих правилах для агентов):

1. `create_session(fileKey, задача)` — до любых файловых инструментов, `sessionId` переиспользуй.
2. Загрузи skill `figma-design-to-code` (обязательно перед `get_design_context`) и наш вход
   `figma-pack:figma-core` (он ведёт в `figma-to-react`).
3. `get_design_context(nodeId)`. Ответ слишком большой — сначала `get_metadata`, потом точечные узлы.
4. `get_screenshot` того же узла — эталон для сверки.
5. Сырые значения переменных — `get_variable_defs`, сопоставляй с токенами проекта, а не вставляй hex.
6. Ассеты бери из источников, которые отдаёт MCP; новые пакеты иконок не ставь.
7. Реализуй через существующие компоненты `shared/ui` и токены; чего нет — сначала компонент кита,
   потом экран. Страница — только после UX-брифа ([react-page-ux](../../skills/react-page-ux/SKILL.md)).
8. Сверка в браузере со скриншотом на 1280 и 375.

Командный пайплайн, который работает даже без прав на запись в Figma:
дизайнер собирает экран из библиотеки → помечает раздел «Ready for dev» → агент читает его (шаги 1–5)
и выдаёт спеку с разделами «нет в макете» и «расхождения токенов» → UX.md → код из кита → сверка → ревью.

## Почему

Ответ MCP не знает о компонентах и токенах проекта. Без шага «сопоставить с китом» каждый экран
плодит хардкод и дубли примитивов, а сверка со скриншотом ловит то, что потерялось при переносе.
